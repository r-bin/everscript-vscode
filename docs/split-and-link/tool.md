# The split/link tool: plan

Status: **design (2026-11-18), nothing built. Partly superseded by [../open-evermore/](../open-evermore/README.md)**:
the tool is `tools/open-evermore/` with explode / implode, one tree keyed by names (no `game/` + `mods/`, no
`<id>-<slug>` folders) and `manifest.json` as the memory map. The link steps (§5), allocator (§5.4), compiler (§7)
and promotion (§10.4) below still hold. This page plans the tool behind [README.md](README.md):

- **`split`** turns the user's ROM into a source tree.
- **`link`** turns the tree, plus your additions, back into a ROM.

It builds on the symbolic export ([symbolic-export.md](symbolic-export.md)). Labels: *(repo)* = exists today;
*(estimate)*; *(to verify)*; *(owner's call)* = a decision for the owner.

**Shape: a `tools/split/` tool** like `tools/sa1/` and `tools/table-hack/`, an L3 lab
([../projects/README.md](../projects/README.md) §1). It reads the compiled `dist/` modules and changes none of
them, apart from two small export hooks, each in its own commit (§10.2). It moves into `src/` only by the
promotion rule (used by two other projects, §10.4).

---

## 1. What the tool does, seen from outside

```sh
npm run split -- --out ~/soe-src              # base ROM of the ROM library + CDL library → tree
npm run split -- rom.smc --out ~/soe-src      # … or a ROM given explicitly (as tools/sa1 takes args[0])
npm run split:link -- ~/soe-src               # tree + mods → ~/soe-src/build/: ROM, symbols, CDL, BPS, report
npm run split:link -- ~/soe-src --check       # unmodified tree → must give the vanilla sha1
npm run split:prove -- ~/soe-src              # link, then replay the stored playbacks against vanilla
```

The inputs are found the way other tools find them *(repo)*:

| Input | How the tool finds it |
|---|---|
| ROM | `require('../rom').baseRomOrExit('evermore', arg)`: the ROM library, never a hard-coded path (`tools/README.md`) |
| CDL library | `--lib <dir>`, default the extension's `globalStorage …/cdl-library`, as `tools/recomp/build.js` does |
| Asar | `--asar <bin>`, then env `ASAR`, then `asar` on `PATH`, then `../asar/asar/bin/asar`, as `tools/recomp/build.js` does |
| knowledge names | `tools/recomp/names.js` `collectNames` *(repo)*, reused |

The VS Code side may get the same as commands, but only after promotion (§9).

**The promise to the user:**

1. A fresh `split`, linked unchanged, gives the original ROM byte for byte.
2. Adding a folder adds content. No address is ever typed by hand.
3. Rebuilding is cheap: only changed items are encoded again.
4. Every link reports, per kind, what changed, where it went and how much room is left.

## 2. The tree

```
~/soe-src/                          never inside a repository (§8)
  split.json                        the manifest (§3): every item, its origin, codec, rule, pin state
  game/                             GENERATED by split; overwritten by the next split; never edited
    asm/<bank>/<routine>.asm        one routine per file, names and comments from knowledge entries
    asm/<bank>/_data_<addr>.asm     data the export could not attribute (db / incbin, pinned)
    tables/<table>.asm              id-indexed tables, as label lists (generated again at link time, §5.3)
    assets/<kind>/<nnn>-<slug>/     one folder per item, shaped like soe://rom/assets/<kind>/
      item.json                     id, codec, properties the codec understands
      *.bin / *.png / *.evs …       the payload in the codec's format
  mods/                             YOURS: same shape as game/, merged over it (§4)
    assets/audio/music/071-my-song/
    asm/patches/faster-text.asm
    layout.json                     optional pins and placements (§5.4)
  build/                            GENERATED by link: out.sfc, out.sym, out.cdl, out.bps, layout.md, cache/
```

**Naming.**

- An item's folder is `<id>-<slug>`. The id is the number the game uses (room 6, song 5); the slug is for
  people and carries no meaning.
- Slugs are our own words or plain kind+id (`room-006`). They never use names from third-party tools
  (AGENTS.md: D3/D4).

**`soe://` shape.** The asset folders use the same paths as `soe://rom/assets/`. The read-only VFS and the
editable tree therefore name things the same way, and deep links between them work (§9).

## 3. The manifest (`split.json`)

The manifest is the "better memory map" of [README.md](README.md) §5.1, written per ROM. Each item has:

| Field | Meaning |
|---|---|
| `path` | where the item lives in the tree |
| `kind` | `code`, `table`, `room`, `string`, `script`, `song`, `sprite-blocks`, `palette`, `raw` … |
| `origin` | file offset and length in the vanilla ROM, sha1 of the original bytes |
| `codec` | which codec writes and reads it (§6), and the codec's version |
| `labels` | the labels it defines, and the labels it references (from the symbolic export) |
| `rule` | placement: half (`lower` / `upper` / `any`), `noCrossBank`, `maxSize`, `bank` (bank-bound), `fast` (must stay in FastROM) |
| `pinned` | `true` when something still reaches it by a raw number; the reason is listed (`raw operand at $8C:1234`, `never ran`, `incbin`) |
| `readers` | from the CDL: who reads it, with the pointer form |
| `table` | for id-indexed kinds: the table it is listed in, the entry format, the engine limit and what sets it |

Only `split` writes the manifest. `link` reads it and never changes it. Facts that hold for any user's ROM
(placement rules, engine limits, reader forms) come from code and knowledge entries, not from the manifest.
The manifest just records them per item.

## 4. Overlay: how mods combine with the game

`link` builds one item list:

- everything in `game/`
- every path in `mods/`, which either **adds** a new item or **replaces** the item at the same path

| What you want | What you do | What link does |
|---|---|---|
| new song | add `mods/assets/audio/music/071-my-song/` | encodes it, gives it id 71, grows both song tables and the count byte |
| change a room | copy the room folder to `mods/`, edit it | uses your version; the room moves only if it no longer fits |
| change a routine | add `mods/asm/<bank>/<routine>.asm` with the same name | your file replaces the generated one; labels referencing it follow |
| hook into a routine | `mods/asm/patches/*.asm` with `pushpc` / `org <label>` + `pullpc` | `incsrc` after all generated files, in name order |
| delete content | a `mods/…/<item>/DELETE` marker | the id stays reserved (the table gets the entry the codec defines as empty) |
| place something | `mods/layout.json` | overrides the allocator for that item (§5.4) |

**Copies of vanilla content.** A mod that starts from vanilla bytes, for example "song 5 under a new id", must
not carry those bytes, or `mods/` would hold ROM data. Instead it holds a reference:

```json
{ "from": "game/assets/audio/music/005-…", "id": 71 }
```

`link` resolves it from the user's own `game/`. Only content you made yourself sits in `mods/` as files.

## 5. Link, step by step

### 5.1 Collect

- Read `split.json`, `game/` and `mods/`; build the item list (§4).
- Refuse when the ROM's sha1 differs from the one `split` saw. The tree is tied to one ROM, US 1.0 only for
  now ([../evermore-releases.md](../evermore-releases.md)).

### 5.2 Encode

- Each asset item goes through its codec (§6) and becomes bytes plus the labels inside it.
- Results are cached by the hash of the item's files plus the codec version.
- Codecs check their own budgets (room ≤ 32 KB, a song within audio RAM) and fail with the item's path.

### 5.3 Generate the tables

- Every id-indexed kind writes its table from the items present: one entry per id, in id order.
- Each entry is a label expression (`dl song_071`), never a number.
- Count bytes are written as `db <count>`.
- Ids above the engine limit fail with the limit's reason (`opcode 0x33 takes a byte offset into $8C:8442:
  128 songs`).
- Gaps follow the kind's rule: a filler entry, or an error.

### 5.4 Lay out

Three rules for placing items:

1. **Stable first.** Every item stays at its vanilla address if it still fits there. Only items that grew, are
   new or were asked to move get a new place. This keeps the vanilla timing for everything untouched
   ([README.md](README.md) §4.5).
2. **Pinned never moves.** Neither do `incbin` runs or items behind raw operands. Growing a pinned item is an
   error that names the pin.
3. **Placement rules.** New and moved items go first-fit into free space that matches their `rule`:
   half, bank, FastROM, no bank crossing.

The free space is:

- the space wiped by moved items
- the 4th MB under the [table-hack.md](../table-hack.md) §1 bank plan, minus the reserved ranges
- under `--map exhirom` or `--map sa1`, the extra space of those layouts

Results:

- `build/layout.asm`: one `org` per placed item
- `build/layout.md`: per bank, used and free, what moved and why
- the directory at `$F1:0000` ([table-hack.md](../table-hack.md) §3): table addresses and free ranges, for the
  everscript compiler and other tools

### 5.5 Assemble

- Generate `build/main.asm`: header, `layout.asm`, then every item's `incsrc` in a fixed order, then
  `mods/asm/patches/`.
- Run Asar (found as in §1), writing `build/out.sfc` and `build/out.sym`.
- Run `build-cdl.js` *(repo)* to carry the CDL flags to wherever labels moved: `build/out.cdl`.

### 5.6 Check and report

| Check | When | Pass means |
|---|---|---|
| **G0** | `--check`, and always when `mods/` is empty | sha1 equals the vanilla ROM |
| budgets | always | every codec and table limit held |
| stable layout | always | every item not listed in `layout.md` as moved is at its vanilla address |
| **G1 / G2** | `--prove` | stored playbacks replay with the same WRAM every frame (`sample-playbacks` skill, `tools/table-hack/prove.js` *(repo)* generalised) |

Outputs besides the ROM:

- `out.bps`: the patch players apply to their own ROM
- `out.sym`: for Mesen, the recomp and the C-to-ROM build
- `layout.md`: the generated memory map of this build

## 6. Codecs

One interface per asset kind, in `tools/split/evermore/codecs/` (formats are per game, AGENTS.md §0.4). A codec
calls the decoders and encoders already compiled in `dist/games/evermore/` and never copies them:

```ts
interface Codec {
  kind: string; version: number;
  /** ROM bytes of one item → files in its folder (+ labels it references, by name). */
  split(rom: Uint8Array, item: ManifestItem): Files;
  /** Folder → bytes, labels defined inside, label references to resolve (Asar expressions). */
  link(files: Files, ctx: LinkContext): { asm: string; budget?: Budget };
}
```

**Two laws:**

1. **Round trip.** `link(split(x))` assembles to exactly `x`. A test runs every codec over every vanilla item
   of its kind (`rom` test tier).
2. **Fall back to raw.** Every item can at least be `raw`: its bytes as `.bin`, its known pointers as labels.
   Splitting never waits for a codec. Editing does.

| Kind | Split (decode) | Link (encode) | Start with |
|---|---|---|---|
| code | symbolic export *(repo, partial)* | Asar | per-routine files from the export |
| tables (168 assets) | `table-assets.ts` *(repo)* | `.asm` as is | as is |
| rooms | `src/games/evermore/maps` *(repo)* | `encode.ts`, `own-room.ts` *(repo)* | full codec: PNG + layers + objects, like the map editor's export |
| strings | decoder *(repo)* | write uncompressed (the key's bit 23 marks compressed ones) *(to verify that the engine reads uncompressed strings everywhere)*; the compressor later | text file per string |
| scripts | `script/`, `script-model/` *(repo)* | the everscript compiler (`.evs` → bytecode), or raw bytes with pointer labels at first | raw + labels; `.evs` once the compiler emits relocatable output (§7) |
| song packages | descriptors only *(repo: `soe://rom/assets/audio/`)* | raw `.bin` | raw; a sequence/sample codec after [../todo/audio-and-music.md](../todo/audio-and-music.md) §1 |
| sprite blocks, palettes | decoders *(repo: `resources/`)* | palettes trivial; blocks: graphics format *(to verify)* | raw, then PNG |
| animation records | `animation-script` decoder *(repo)* | encoder missing | raw; bank-bound to `$C4` |
| projectiles | — | schema compiled into several tables ([README.md](README.md) §3.2) | after the tables it spans have codecs |
| everything else | — | — | `raw`, pinned until its readers are known |

## 7. The everscript compiler

The compiler (sibling repo, Python) allocates its own space today (`compiler/linker.py`, `MemoryManager`
*(repo)*). The tool needs it to fit in, in two stages:

1. **Now: reserved range.** `link` reserves a range per build and passes it to the compiler as `#memory`; the
   compiler output goes in as a `raw` item at a pinned address. This works with no compiler change.
2. **Later: relocatable output.** The compiler writes `.asm` with labels (or objects with relocations) into
   `mods/everscript/`, and `link` places it like any other item. Script ids, string keys and function keys then
   come from the generated tables (§5.3), not from the compiler's own `string_key(..)` / `function_key(..)`
   ranges. This is a change in the compiler's repo, so it needs that repo's owner *(owner's call)*.

## 8. Legal and repo rules

- **Where the tree lives.** `split` writes outside the repository by default. Inside the repo, it must go under
  a git-ignored folder (`out/`). `check:legal` already blocks ROM-derived files.
- **What gets committed (here):**
  - the tool
  - codecs
  - placement rules and limits
  - knowledge entries (names, comments)
  - tests that use synthetic data, or the user's ROM at test time

  Nothing produced by `split`.
- **What a modder may share:** `mods/` (own content and references, §4) and `out.bps`. Never `game/` or
  `out.sfc`.
- **Names.** Generated names come from knowledge entries (our own words). Folder slugs follow §2.

---

## 9. Editor integration (after promotion only)

A tool in `tools/` has no VS Code side. Until promotion (§10.4), the editor connects in only one way:
opening `build/out.sfc` through the ROM library or `soe://rom/…?rom=<path>`, which needs no code. After
promotion:

- **Commands:**
  - *Split ROM to folder…*
  - *Link folder*, with the result in the status bar and `layout.md` opened on failure
  - *Prove build* (playbacks, in the background)
- **The editors write into the tree.** The Rooms map editor saves a room to `mods/assets/maps/<id>-…/`
  instead of patching a ROM. The script editor saves `.evs` to `mods/`.
- **Reading the build.** `soe://rom/…?rom=<tree>/build/out.sfc` shows the linked ROM in every existing tab
  without new readers *(repo: `?rom=<path>` exists)*.
- **Links.** Hovering a label in `game/asm` shows its knowledge entry; `layout.md` links each item to
  `soe://` and to the tab that edits it (`vfs-and-knowledge` skill).

## 10. The tool's files

### 10.1 Layout of `tools/split/`

TypeScript `.mts`, run directly by Node like `tools/sa1/` (AGENTS.md §0.8: TS by default).

```
tools/split/
  README.md            what it is, how to run it, the tree (§2), links to these docs
  AGENTS.md            invariants (G0 always, no ROM bytes in the repo, stable layout) and its tests
  split.mts            CLI: ROM + CDL library → tree; writes split.json; runs link --check at the end
  link.mts             CLI: tree → build/ (§5); --check, --map hirom|exhirom|sa1
  prove.mts            CLI: link, then replay the playbacks (wraps the replay of tools/table-hack/prove.js)
  manifest.mts         split.json types, read/write, validation
  overlay.mts          game/ + mods/ → item list; `from` references; DELETE markers (§4)
  symbolise.mts        the symbolic export passes M1–M5, as hooks handed to the export (§10.2)
  routines.mts         one file per routine: cuts the export's bank text at function labels (P1)
  tables.mts           id-indexed tables generated from the items present (§5.3)
  layout.mts           the allocator: stable first, pins, placement rules, free space per --map (§5.4)
  directory.mts        the $F1:0000 directory (table-hack.md §3)
  assemble.mts         main.asm, Asar, build-cdl.js, out.sym
  bps.mts              BPS patch writer
  report.mts           layout.md, the ratchet counts, budget failures
  evermore/
    regions.mts        what is an item: rooms, strings, tables, songs …; reuses dist/games/evermore/cdl/regions
    rules.mts          placement rules and engine limits per kind, each with its source (knowledge entry / doc)
    codecs/            one file per kind (§6): raw, code, table, room, string, song, palette …
```

The `evermore/` subfolder is the only place with game facts. A second game would get a sibling folder; nothing
in the other files may name Evermore (AGENTS.md §0.4).

### 10.2 What it reads from `dist/`, and the only changes outside `tools/split/`

The tool only *calls* these *(repo)*:

- `dist/platform/cdl/`: `library` (the CDL library), `rom-map`, `asar-export`, `xref-index`, `library-ext` (regs,
  bases), and `asar-kit/build-cdl.js`
- `dist/games/evermore/cdl/regions` (`evermoreRegions`)
- `dist/games/evermore/maps` (decode and encode rooms)
- the string, script and resource decoders
- `dist/platform/tas/movie` (playbacks)

The symbolisation (M1–M5) belongs to the tool, but it has to act *while* the export writes its text. Rewriting
the text afterwards would mean parsing assembly again. So `asar-export.ts` gets two optional hooks, each a small
L1 change in its own commit ([../projects/README.md](../projects/README.md) §1):

| Hook | Called for | Default (no hook) |
|---|---|---|
| `resolveOperand(ins, bus, width, ctx)` | every operand the built-in `resolve` leaves as a number | number, as today |
| `writeDataRun(start, end, ctx)` | every data run before it becomes `db` / `dw` | as today |

With no hooks, the export stays exactly as it is, so the CDL tab and `npm run recomp` do not change. Fixing M0
(the missing `gameRegions` in `tools/recomp/build.js`) is a separate one-line commit in `tools/recomp/`.

### 10.3 Tests

| Test | Tier | What |
|---|---|---|
| `tests/split/overlay.test.mts`, `layout.test.mts`, `tables.test.mts`, `bps.test.mts` | unit (`npm test`) | synthetic items and banks; no ROM |
| `tests/split/round-trip.test.mts` | `rom` | every codec over every vanilla item of its kind: `link(split(x)) = x` |
| `tests/split/g0.test.mts` | `rom` | split + link of the base ROM gives the vanilla sha1; skipped when no Asar is found |
| `npm run split:prove` | on demand | playbacks; never in a test tier (`test-discipline` skill) |

### 10.4 Promotion

The tool stays in `tools/split/` while only it uses its parts. A part moves when two other projects need it:

- the allocator and the directory, when the everscript compiler and the table hack read them
- the codecs, when the Rooms tab saves into the tree

The game-neutral parts would go to `src/platform/split/`, the codecs and rules to `src/games/evermore/split/`
(`architecture` skill, `src/README.md` layer rules).

## 11. Phases

Each phase ends with something usable and a check that proves it.

| Phase | Deliverable | Proof | Depends on |
|---|---|---|---|
| **P0 skeleton** | `tools/split/` with `split.mts` (today's export with `gameRegions` + `split.json`, all items `raw` or `code`, pin states), `link.mts` (Asar + `build-cdl.js`), npm scripts, README, AGENTS.md | G0 on a fresh split (`tests/split/g0`) | M0 in `tools/recomp/` (own commit) |
| **P1 one file per routine** | `routines.mts`: `game/asm/<bank>/<routine>.asm` instead of one file per bank; data runs as their own items | G0 | — |
| **P2 symbols** | the two export hooks (own commit, §10.2); `symbolise.mts` with M1, M2; the ratchet counts in `report.mts`; pins from the remaining raw operands | G0; the counts in the link report | P0 |
| **P3 overlay + tables + stable layout** | `mods/` merge, generated tables, the allocator with placement rules, `layout.md`, directory | G0 with empty `mods/`; a moved table proven with `--prove` | P2 |
| **P4 first codecs** | rooms (full), strings (uncompressed write), tables, palettes; round-trip tests | round trip on every vanilla item | P3 |
| **P5 first vertical slice: songs** | `music/` folders generate `$8C:8442` and `$81:9903` + count; `from`-references | song 5 copied to id 71 plays from a script; vanilla playbacks still identical (G2) | P3, reader census for both tables |
| **P6 bank-bound pools** | M3 for `$8E`: character records as items, enemies as folders | the table hack's enemy test (a new enemy spawned) passes without the table hack | P3 |
| **P7 projectiles** | the projectile schema over its tables | a new projectile launched by `0xB5` | P6, `$90:D986` census |
| **P8 compiler, then promotion** | everscript reserved range (§7 stage 1); then the promotion of §10.4 and the §9 commands | `split:link` builds an everscript mod; after promotion, the Rooms tab saves a room, `split:link` builds it, the room loads in the emulator | P4 |

Sizes *(estimate)*: P0–P1 a few days; P2 a week; P3 one to two weeks; then about a week per codec or slice.

## 12. Open questions

1. **Command names.** Is `split` / `split:link` / `split:prove` right, or should the tool have a name of its
   own? *(owner's call)*
2. **Where the tree lives.** A fixed default (`~/soe-src`), or chosen on the first split? *(owner's call)*
3. **Splitting again after new CDL data.** It changes `game/` (more routines, fewer pins). `mods/` must survive
   it. A mod that replaces a routine must be told when the generated original changed, so the tool should
   keep the original's hash in the mod *(proposal)*.
4. **ExHiROM / SA-1 as link targets.** One flag on the same tree, or separate trees? Proposal: a flag; the
   layout rules per target come from [../exhirom/layout-options.md](../exhirom/layout-options.md).
5. **The table hack.** Once P3 proves a moved table, does `tools/table-hack/` stay as the no-Asar route or
   retire? *(owner's call)*
