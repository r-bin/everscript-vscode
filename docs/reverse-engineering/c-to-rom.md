# From reconstructed C to a game that plays identically

> Status: **plan**, written 2026-10-24 (v0.343.0), revised the same day after comparing with
> working decomps. The question: how do the C files in `reconstructed-c/` become code that
> runs the game so it looks and plays exactly like the original?
> Read with: [asm-to-c-port.md](asm-to-c-port.md) (stages, the Asar export, lockstep),
> [../recomp/lessons-from-mmx-and-lufia2.md](../recomp/lessons-from-mmx-and-lufia2.md) (two more
> snesrecomp ports, read 2026-10-21), [../recomp/README.md](../recomp/README.md).

---

## 0. Short answer

None of the working SNES decomps compiles its C back into a SNES ROM. zelda3, smw and the
Super Metroid recomp (below), and MMX and Lufia 2 before them, all build a **PC program**.
The game logic is C, the PPU/DSP (or the whole SNES apart from the CPU) is emulated, and the
user's ROM is the input (assets) and the **reference**: the C is accepted only when RAM
matches the ROM, every frame, on the same inputs. That per-frame comparison is how those
projects get "looks and feels identical". Byte matching plays no part in any of them.

So we follow the same method, with the tools we already have:

1. **Run:** the snesrecomp build (`npm run recomp`, boots since v0.201.10). A verified C
   routine replaces the original through `hle_func` (Super Metroid, MMX and Lufia 2 do this);
   everything else keeps running the ROM's code.
2. **Prove:** a per-routine differential test against the ROM's own bytes (Lufia 2), then a
   per-frame RAM comparison against the original ROM over recorded inputs (zelda3, smw).
3. **Later, optionally:** once the engine is C, the hand-written C can stand alone with
   emulated PPU/APU, as zelda3 and smw do.

**A ROM** still comes from the Asar export, which already rebuilds byte-identically. ROM
edits remain asm patches (`snes-asm-asar-patching`). Compiling C into 65816 code would be new
territory: none of these projects does it, so it is not on the plan (§8).

## 1. How the working decomps do it

Read 2026-10-24 from each project's README and, for zelda3, its comparison source
(`src/zelda_cpu_infra.c`). This page describes their ideas in our own words. No code or data
was taken. Licences: zelda3 MIT; SuperMetroidRecomp and snesrecomp PolyForm Noncommercial.

| | [snesrev/zelda3](https://github.com/snesrev/zelda3) | [snesrev/smw](https://github.com/snesrev/smw) | [mstan/SuperMetroidRecomp](https://github.com/mstan/SuperMetroidRecomp) | SoE today |
|---|---|---|---|---|
| Output | PC executable | PC executable | PC executable | Asar ROM (byte-exact); recomp executable (boots) |
| Where the C comes from | written by hand, whole game (~70–80k lines) | written by hand, whole game | generated by snesrecomp, not committed; hand-written runtime and HLE bodies | 258 hand-written files that are not compiled; recomp C generated |
| What is emulated | PPU and DSP (LakeSnes) | PPU and DSP (LakeSnes) | everything but the CPU ("recompile the CPU, emulate the silicon"); unproven code runs on an interpreter | everything but the CPU |
| ROM's role | assets extracted once into a data file; optional at run time for the comparison | same | read at build and run time, never redistributed | read at build and run time |
| The proof | runs the original code on an emulated CPU beside the C and compares RAM after every frame | "runs an emulated version in the background and compares the ram state every frame" | replays recorded sessions, checks WRAM, CPU, APU RAM and VRAM, stops at the first divergence; a strict regeneration must be byte-identical | `npm run recomp:lockstep`: WRAM against our snes9x core at the same NMI counter |
| On a mismatch | logs the differing bytes, restores the pre-frame state | saves a snapshot (with input history) for a bug report | stops at the first divergence | prints the differences |

What zelda3's comparison does in detail, because it is the most mature one:

- **What it compares:** all 128 KB of WRAM, the SRAM and the first half of VRAM, after each
  frame.
- **What it excludes:** before comparing, it copies a list of addresses from one side to the
  other. These are temporaries, the RNG state, IRQ flags, the stack area, HDMA leftovers. They
  are bytes whose value no later code depends on, or that legitimately differ.
- **It patches the original, not just the C:** before the reference run, a handful of ROM
  bytes are changed. That removes reads of uninitialised memory and carry flags, makes the RNG
  deterministic, avoids one known out-of-bounds bug and disables a loader that hangs the
  emulator. The reference is "the original, made deterministic", and each patch is listed in
  one place.
- **Snapshots carry the input history**, so a reported mismatch can be replayed.

Lufia 2 (see the lessons page, §3) adds what the frame comparison alone misses. Before a C
routine is bound, it is tested against the ROM routine on captured entry states. The test
covers CPU, full WRAM, I/O and the order of memory accesses, and the ROM routine is
deliberately mutated to prove the test can fail.

## 2. Where our C stands

Measured on 2026-10-24 over `reconstructed-c/` (258 files, ~18,900 lines, ~550 functions):

| Finding | Count | Why it matters for running it |
|---|---|---|
| Files that fail `clang -std=c99 -fsyntax-only` | 45 / 258 | mostly undeclared functions; two are prose examples, not routines (`808100_how_to_create_a_game_decomp.c`, `FFFFFF_*`) |
| Files declaring their own `extern` WRAM globals | 224 | no shared header; 898 distinct extern names |
| WRAM addresses with more than one name | 32 | e.g. `$7E:0100` is both `g_frame_counter` and `g_frame_counter_lo` |
| Routines with two files | 8 | `80A1B4_hdma_gradients.c` and `80A1B4_weather_blending.c` |
| Raw ROM pointer casts (`*(const uint16_t *)0x928002`) | 11 files | dereferences a host address; must read the ROM image instead |
| `float` / `double` | 2 files | the original is fixed-point; floats round differently |
| snesrecomp machine C (`CpuState *cpu`) | 3 files | generated code, not decompiled C |

Most files are **descriptions in C syntax**. They give the control flow but change the
interface. `random_below` is typical ([8080AD62_random_below.c](../../reconstructed-c/80/8080AD62_random_below.c)):

| | The ROM routine (`80ad62.md`, `docs/disassembly/combat/random-below.md`) | The C file |
|---|---|---|
| input | the word at direct page `$02` | a function parameter |
| work | 8×8 hardware multiplier `$4202/$4203`, partial products in DP `$0A–$0D` | one 32-bit multiply |
| output | A | return value |

Both compute the same number. Only the ROM's version can be called by the asm callers that
remain, though, and only it leaves the same WRAM behind. Our lockstep list of "noise" bytes
(`tools/recomp/lockstep.js`, `$02–$0E`) would hide exactly that difference. That is the
reason for a per-routine test (§4, G1) in addition to the frame comparison.

PROGRESS.md counts these files as "clean C". By the gates of §4 none has passed G1 yet.

## 3. Example: one routine, end to end

`random_below` (`$80:AD62`) is a good first routine: small, called from combat, one callee
(the generator `$80:859B`), no PPU. These are the steps, with what exists and what has to be
built.

**Step 1: read the original and write down its interface.** `soe://rom/code/random_below/random_below.asm`
(MCP `soe_read`) and the CDL widths. Note in `80ad62.md`: entry widths, input DP `$02`,
output A, the flags it leaves, scratch DP `$0A–$0D`, whether it ends in `RTS` or `RTL`, and
the cycles per call (from the CDL library's `bus.json`).

**Step 2: write the C against WRAM, as the original does.** The routine reads its input from
WRAM and leaves its scratch where the original does. A zelda3-style generated header names
each address once, as an accessor over the one RAM array (`g_ram` in snesrecomp's runner).

```c
/* reconstructed-c/80/8080AD62_random_below.c, target shape */
#include "soe_ram.h"            /* generated from knowledge/ram/*.md: one name per address */

/* $80:AD62. In: n = DP $02. Out: A = rand16 * n >> 16 (0 when n == 0).
 * Advances the generator ($80:859B) even when n == 0. Leaves the partial
 * products in DP $0A-$0D. */
uint16_t random_below(uint16_t dp)
{
    uint16_t n = ram16(dp + 0x02);
    uint16_t r = random_number_generator();
    uint32_t p = (uint32_t)r * n;
    /* the four scratch bytes: written as the 8x8 steps leave them (from the .asm) */
    ...
    return (uint16_t)(p >> 16);
}
```

**Step 3: bind it with `hle_func`** (snesrecomp `docs/HLE_FUNC.md`). The bridge gets the CPU
state at the routine's first instruction and must leave the state its last instruction
leaves. That includes A, the flags, and the return frame popped by the original's return
opcode: 2 bytes for `RTS`, 3 for `RTL`.

```c
/* tools/recomp/host/src/hle_soe.c (to be added) */
RecompReturn Hle_random_below(CpuState *cpu)
{
    cpu->A = random_below(cpu->D);
    /* set N/Z/C as the original's last instructions leave them */
    cpu->S += 3;               /* if the .asm ends in RTL */
    return RECOMP_RETURN_NORMAL;
}
```

```text
# appended to the generated bank80.cfg (mechanism to add to tools/recomp)
hle_func ad62 Hle_random_below
```

Inside the C, the generator is called through its generated alias until it is in C itself.
The stub charges no cycles. A bridge that takes no time makes busy frames faster than on the
SNES, and the game no longer slows down where the original does. To keep the same feel, the
bridge adds the original routine's cycle cost to the runner's cycle estimate.

**Step 4: G1, the per-routine test** (Lufia 2's method, in our tools). Capture real entry
states for `$80:AD62` from the stored playbacks (`sample-playbacks`): WRAM plus registers at
each entry. Add generated edge cases: n = 0, 1, `$FFFF`, and generator states around wrap.
Run the ROM's bytes in `src/platform/snes/cpu65816.ts` and the C bridge on the same states,
then compare A, flags, S and all WRAM, with no noise list. Then flip one instruction of the
ROM routine (e.g. use the low word of the product instead) and check that the test fails.

**Step 5: G2, A/B in the recomp.** Build with and without the binding (snesrecomp regenerates
without any `hle_func` on request). Replay the same playback in both. WRAM must agree every
frame. This comparison does not suffer from the recomp's timing drift against snes9x, because
both sides are the recomp.

**Step 6: G3, against the original.** Run `npm run recomp:lockstep`, extended to replay
recorded input instead of running without input. Every exclusion goes in one list with its
reason, as in zelda3.

**Step 7: record.** Write the gate in the C file's header and in `80ad62.md`. Write new facts
per the `game-knowledge` skill.

## 4. Gates: when a routine counts as done

PROGRESS.md and `soe://rom/code/todo.md` count by gate, not by "a C file exists".

| Gate | Check | Learned from |
|---|---|---|
| **G0** | Compiles on the host with `-Werror` against the generated headers: no local `extern`, no float, no raw pointers | — |
| **G1** | Equal to the ROM's own bytes on captured and generated entry states: registers, flags, S, full WRAM, I/O writes in order; a deliberate mutation of the ROM routine is caught | Lufia 2 |
| **G2** | The recomp with the binding equals the recomp without it, every frame, on recorded playbacks | MMX, Super Metroid (`--no-hle` A/B, stop at first divergence) |
| **G3** | Per-frame WRAM (+ VRAM, CGRAM, OAM) equal to the original ROM in snes9x on recorded playbacks, with one documented exclusion list | zelda3, smw |

G1 runs on every edit (ROM tier). G2 and G3 run on demand (`test-discipline`).

## 5. The C form

The rules every routine's C follows to pass G0–G1:

- **One RAM header, generated.** `soe_ram.h` from `knowledge/ram/*.md`: one name per address,
  an accessor over `g_ram` (zelda3 does this with a header of names over one RAM array). Fix
  the 32 double names first. Records are structs with `_Static_assert` on each field offset.
- **Interface as the ROM has it.** Inputs and outputs live where the asm keeps them (registers,
  DP slots, flags). A parameter in the C body is fine. The bridge takes it from the original's
  place and puts the result back there.
- **Scratch is WRAM.** DP temporaries the original writes are written the same way, or the
  routine's knowledge entry states that no reader exists (and G1 compares them either way).
- **Widths as the machine has them.** `uint8_t`/`uint16_t`/`int16_t`, explicit casts where
  the asm wraps at 8 or 16 bits, no `int`-sized assumptions, no floating point.
- **ROM data from the ROM image** (`g_rom` in the runner), by named table offsets from the
  export, never copied into the repo.
- **One routine, one file**, named as in the knowledge entry, with the gate in its header.
  Prose examples move to the docs that quote them.

## 6. Order and what stays on the ROM's code

- **Leaves first**, then their callers, one subsystem at a time. Start with decoders already
  verified in TypeScript for the map editor (LZSS `$8C:988D`, the room blob layout), then math
  and RNG (`random_below`), text, entities, combat, the room loader.
- **Stays original code (LLE) for now:** NMI (`$80:823A`), the IRQ handler
  (`8084EE_irq_dispatch.c`), the SPC upload and handshake (`$8C:805C`, `$8C:81FD`), HDMA
  setup, anything that polls `$4212` or uses exact cycle timing. The Super Metroid and MMX
  ports keep such code on the interpreter, too.
- **Scripts** are bytecode and stay bytecode (everscript). Only the engine becomes C.

## 7. Traps

- **Noise lists hide bugs.** The frame comparison needs exclusions (zelda3 has them, our
  lockstep has `$02–$0E`), but each one is a place a C routine can be wrong unseen. G1 has no
  exclusions; G3's list is short, shared and justified per byte.
- **The stack page is WRAM.** C that pushes differently leaves different bytes below S.
  Compare `$0100–$01FF` only above S, decided once in the harness.
- **Lag frames are part of the feel.** Native C runs faster than the 65816. Charge each bound
  routine's original cycles (§3, step 3), or slowdown and frame-timed events change.
- **The reference may need to be deterministic.** If the original reads uninitialised memory
  or seeds from hardware counters (our lockstep already copies the RNG state `$0133–$013A`),
  fix that once in the reference run and list it, as zelda3 does with its ROM patches.
- **The asm is the oracle, not the old C file.** When they disagree, the old file is wrong.
- **US ROM only** (`docs/evermore-releases.md`). **No third-party disassembly** (`AGENTS.md`):
  interfaces come from our export, CDL and traces.

## 7a. Measured: a C-built ROM must be cycle-exact to keep WRAM per frame

Measured 2026-10-24 (v0.344.0) on the bundled snes9x core against the reference recording
`intro-2m20.evsmv` (power-on, no input, 8414 frames: logo, intro, logo; `tools/c-to-rom/`).
The owner then asked for C compiled into the ROM after all, with WRAM identical to vanilla
every frame. These are the facts that goal runs into.

- **The main thread is busy at almost every NMI.** In those 8414 frames the NMI (`$00:823A`)
  interrupted the main thread inside `wait_for_nmi` (`$80:858C`) 674 times. Everywhere else it
  hit entity and collision code (`$8F:98xx`, `$8F:A3xx`, `$90:9DE8`). The engine time-slices: how
  much work lands in a frame depends on how long it takes.
- **Any cycle difference diverges for good.** A detour through the 4th MB (`JML` out and back,
  no other change) adds about 8 cycles per call:
  - on `random_number_generator` (`$80:859B`, 23,509 calls), WRAM differs from frame 474 in
    7928 of 8414 frames;
  - on `eval_tile_collision` (`$90:9DE8`, 723,906 calls), with the RNG frozen in both images
    (state stored as 0, returns 0), WRAM still differs from frame 474. Entity records
    (`$4E89+`, `$5018+`) differ, and by frame 8413 the scene counter `$0100` differs too
    (2157 vs 2161).
  Freezing the RNG removes one source of divergence, not the dependence on time.
- **So:** WRAM identical every frame requires the compiled code to take exactly the
  original's master cycles on every path it runs during the recording. A stock compiler
  cannot promise that.
- **Calypsi** (checked 2026-10-24, v5.18 of 2026-07-17; closed source, licensed for private
  use; SNES target since 5.12): the macOS package ships x86_64 binaries, which run on Apple
  Silicon under Rosetta 2. Its ABI reserves 32 direct-page bytes for pseudo-registers and puts
  DP and the stack in bank `$00`. On the SNES that is WRAM `$0000–$1FFF`, so its code writes
  WRAM the original does not, unless every bound function saves and restores those bytes.
- **The reference is deterministic:** the same ROM replayed in another process gives the
  same WRAM CRC on all 8414 frames, and a 4 MB image with nothing changed (the 4th MB
  mirroring the first, as `tools/table-hack/tables.js` builds it) equals vanilla on every frame.

The architecture overview for compiling C into HiROM (linker regions, near/far pointers) is
[c-compilation-hirom-memory-map.md](c-compilation-hirom-memory-map.md).

## 8. Not pursued: compiling the C into the ROM

The first version of this page planned a C dialect and our own 65816 compiler to put C into
the ROM, byte-exact. No project above does this. Hand-written 65816 has no compiler output
to match, and stock 65816 C compilers use their own calling conventions and produce slower
code. That would be research, not a known-working method. What remains:

- **A ROM, byte-exact:** the Asar export (stage 1), already done.
- **A changed ROM:** asm patches; new code may come from a stock 65816 C compiler in free
  ExHiROM space behind an asm trampoline (`snes-asm-asar-patching`). None of it replaces
  original routines.
- **Romhacks in the C port:** smw reimplements Lunar Magic's features in C, so hacked levels
  load. For us, the port reads rooms, scripts and tables from the user's ROM at run time,
  which the recomp already does, and edited ROMs keep working.
